# STFU Architecture

STFU (Skyrim Talk Filter Utility) is an SKSE plugin (`STFU.dll`) plus a PrismaUI React menu that silences or prevents NPC dialogue and ambient scenes. It runs in-process with direct access to engine structures through CommonLibSSE-NG. It works by hooking the engine's dialogue pipeline, checking each line against user rules stored in SQLite and toggles held in `TESGlobal`s from `STFU.esp`, and then either stopping the line ("hard block") or letting it run with its audio, subtitle and animation removed ("soft block"). Scenes are also gated before they start, by adding a condition to each of their phases.

This document gives the map. For more detail on any area, follow the links in [Related docs](#related-docs).

## Startup sequence

This is the order of the code in `src/main.cpp`.

**`SKSE_PLUGIN_LOAD`** (runs when SKSE loads the plugin, before any game data exists):
1. `Logger::Setup()` creates `STFU.log` (truncated each launch) and picks the debug or info level from `stfu_debug.flag`.
2. `SKSE::Init(a_skse, /*a_log=*/false)` initializes SKSE. `false` stops SKSE replacing STFU's logger.
3. Registers `MessageHandler` with the messaging interface. If that fails, it returns `false` and the plugin does not load.
4. Registers `PapyrusInterface::RegisterFunctions` with SKSE's Papyrus interface.

**`kDataLoaded`** (all plugins are loaded, the form tables exist, and there is no save yet):
1. `Config::Load()` runs `GenerateDefaultYAMLs()` and `InitializeHardcodedScenes()`, then looks up the 5 master globals and the per-subtype globals by EditorID (`TESForm::LookupByEditorID`). A missing `STFU.esp` shows up as `Global '...' not found in loaded ESPs` warnings.
2. It creates `Data/SKSE/Plugins/STFU/data/` and calls `DialogueDB::GetDatabase()->Initialize(dbPath)`, which opens SQLite in WAL mode, creates and updates tables and indexes, prepares statements and calls `DialogueLogger::Initialize()`.
3. **This step runs only if the DB initialized:**
   - First-run import, gated by the meta flag `hardcoded_scenes_initialized`: `ImportHardcodedScenes(GetHardcodedScenesList())` and `ImportHardcodedScenes(GetFollowerCommentaryScenesList(), "FollowerCommentary")`, then it sets the flag.
   - `SettingsPersistence::LoadSettings()` copies INI values into the globals and the hotkey.
   - `SceneMonitor::Initialize()`: on the first run (meta flag `bard_scenes_initialized` unset) it imports the scenes of the two bard quests (`Config::GetBardSongScenesList()`) as `BardSongs` rows, insert-only so existing rows are left untouched.
4. It sets up the trampoline: 256 bytes from SKSE's branch pool, or `trampoline.create()` if that pool is unavailable. CommonLib v9's `AllocTrampoline` no longer falls back.
5. It installs the hooks in this order: `PopulateTopicInfoHook::Install()` (Detours), `SceneHook::Install()` (only logs "Scene blocker ready"), `ConstructResponseHook::Install()` (two `write_call<5>` at +0x61 and +0xDE, each guarded by an E8 check), then `DialogueItemCtorHook::Install()` (Detours).
6. `PrismaUIMenu::Initialize()` requests the PrismaUI API, runs `CreateView("STFU/index.html", OnDomReady)`, registers the JS listeners and hides the view.
7. It registers `InputEventSink` with `BSInputDeviceManager`. The sink checks the hotkey and calls `PrismaUIMenu::Toggle()`.
8. It registers `LoadingMenuSink` with `RE::UI`.
9. `SceneHook::PatchScenes()` does the initial condition patching of every hard-blocked scene, every bard scene and every scene that contains a hard-blocked topic.
10. It logs `STFU initialized successfully`.

**Loading Menu sink** (`LoadingMenuSink::ProcessEvent`): when `"Loading Menu"` is **opening**, it calls `SceneHook::PatchDeferredScenes()`. That drains the in-memory queue of scenes that were playing when a live Hard-block update tried to patch them. By the time the load screen opens, the engine has stopped those scenes, so patching is safe. This happens on every load screen: doors, fast travel and save loads.

**`kPostLoadGame`** (after each save load):
- `SettingsPersistence::LoadSettings()` runs again. The save restores the global values it holds, so this reapplies the INI and keeps settings global across saves.
- `DialogueDB::GetDatabase()->FlushQueue()`.

**`kNewGame`**: `SettingsPersistence::LoadSettings()`.

**`kPreLoadGame`**: does nothing.

> Scene conditions are patched into the in-memory `BGSScene` forms once, at `kDataLoaded`. They are not saved to the save file and are not redone on load. Because the gate compares against a global, flipping a toggle takes effect without re-patching.

## One line of dialogue, end to end

This is the high-level path. [DIALOGUE_HOOKS.md](DIALOGUE_HOOKS.md) has the full order of evaluation and the dedup rules.

1. **`DialogueItem::Ctor`** (`main.cpp` `Hook_DialogueItemCtor`, ID 34413/35220). This hook calls `PopulateTopicInfoHook::RecordDialogueConstruct(speaker, topicInfo, topic)` with a timestamp and then calls the original constructor. It never blocks anything. It only feeds the history correlation. The record comes before the PopulateTopicInfo call it is matched to. That fits the ctor calling PopulateTopicInfo internally, but this has not been checked by disassembly.
2. **`PopulateTopicInfo`** (`PopulateTopicInfoHook.cpp` `Hook_PopulateTopicInfo`, ID 34429/35249) is the single decision point.
   - It reads the line's text with `TopicResponseExtractor::ExtractResponsesFromTopicInfo`.
   - It runs a duplicate check through `ConstructResponseHook::IsDuplicateDialogue` (same TopicInfo and speaker within 5 s). A duplicate reuses the cached decision and skips everything else.
   - **Hard block**: if a DB blacklist entry of type `Hard` matches the topic (by EditorID, or ESL-safely by quest + plugin + local FormID), the hook logs the line to history and **returns 0 without calling the original**. Nothing downstream runs.
   - **Soft block decision**: `Config::ShouldSoftBlock(...)` is evaluated with the full actor context. The result is **cached** with `ConstructResponseHook::SetBlockingDecision(soft, topicInfoFormID)`, which is `thread_local`. If the result is a block, the hook clears `a_responseData->responseText` and calls `SetEarlyBlockFlag(true)`.
   - It then calls the original PopulateTopicInfo. The two call-site hooks below fire inside that call.
3. **`SetSubtitle`** (the `write_call` at +0x61) runs first because its call site comes first. `Hook_SetSubtitle` passes `""` instead of the text when `g_shouldBlockCurrent` is set. **This is where subtitles are blanked.**
4. **`ConstructResponse`** (the `write_call` at +0xDE). `Hook_ConstructResponse` reads the cached decision. If none was cached, it re-evaluates without the actor. It then does one of the following:
   - For a bard song with the bard toggle on, it sets `scene->isPlaying = false` and returns `false`.
   - Otherwise it calls the original, and then, for a soft block:
     - Scene lines (subtype 14): it blanks the text and overwrites the file path with `Sound\STFU\silent.fuz` so the scene keeps advancing.
     - Other lines: it clears the file path, text, idles, emotion and flags. **This is where audio is removed.**
5. **Back in `Hook_PopulateTopicInfo`, after the original returns**, it decides whether to write history. The line must have text, must not come from the player, and must pass the grunt/breath filter. It must also have a matching Ctor record less than 50 ms old, not be on the 5 s (speaker, TopicInfo) cooldown, and not be an unchosen candidate in a burst: another TopicInfo of the same Topic within 100 ms, where this one is not in `MenuTopicManager::dialogueList`. Finally it must not repeat the same speaker's text within 5 s and the speaker must be no more than 5000 units away. If all of that holds, it calls `DialogueDB::LogDialogue(entry)` and runs blacklist enrichment. **This is where history is recorded.**
6. **`LogDialogue`** writes the line to `STFU_DialogueLog.txt` immediately. It also queues the DB row. The queue is flushed inline when it reaches 200 entries or 1 s has passed since the last flush (`FLUSH_INTERVAL_MS`; there is no timer, so the check only runs when the next line is logged). After a flush, a UI refresh is posted to the main thread.

Scenes have a separate gate that runs earlier. A hard-blocked scene never starts, because each phase's start conditions begin with `GetGlobalValue(<category global>) == 0`, and a global value of `1` means blocked. None of the steps above run for it. See [SCENE_BLOCKING.md](SCENE_BLOCKING.md).

## Threading at a glance

| Code | Thread | Evidence |
|---|---|---|
| Dialogue hooks (Ctor, PopulateTopicInfo, SetSubtitle, ConstructResponse) | Engine worker threads (BSJobs). Several can run at once, for example on the first frame after a load. On VR it may be the audio thread. | Code comments in `Config::GetSubtypeName`, `EditorID.h` and `DialogueDatabase_History.cpp` `ProcessQueue`. Not checked independently. |
| The decision cache in `ConstructResponseHook` (`g_shouldBlockCurrent`, `g_shouldSoftBlock`, ...) | `thread_local` | This works only because SetSubtitle and ConstructResponse are called *inside* PopulateTopicInfo on the same thread |
| History correlation state (`g_recentConstructs`, cooldown maps) | Shared, and guarded by `g_constructMutex` / `g_loggedMutex` | `PopulateTopicInfoHook.cpp` |
| SQLite access | The caller's thread, under `dbMutex_` (recursive). There is **no dedicated DB thread**. The history queue (`queueMutex_`) is flushed inline by whichever thread crosses the batch or time threshold. `queueMutex_` and `dbMutex_` are never held together (an invariant). | `DialogueDatabase_History.cpp` `LogDialogue` / `ProcessQueue` |
| `MessageHandler`, `InputEventSink`, `LoadingMenuSink` | Main thread | Standard SKSE/engine dispatch |
| PrismaUI JS listener callbacks and `OnDomReady` | Main thread. PrismaUI wraps each callback in `SKSE::GetTaskInterface()->AddTask`. | `.resources/PrismaUI/framework/src/API/API.cpp`. This is the reference framework source; the version installed in game has not been checked. |
| Papyrus natives (`PapyrusInterface`) | Papyrus VM thread. `ImportHardcodedScenes` also starts a detached `std::thread`. | `PapyrusInterface.cpp` |
| Scene condition edits at runtime (`UpdateSceneConditions*`) and UI refresh after a DB flush | Posted to the main thread with `SKSE::GetTaskInterface()->AddTask` | `SceneHook.cpp`, `DialogueDatabase_History.cpp` |

Invariants:
- Never call PrismaUI from inside a DB lock. Post the call with `AddTask`.
- Never edit `BGSScene` conditions off the main thread.
- Never add conditions to a scene where `isPlaying` is true. The NPCs soft-lock. Queue the scene for `PatchDeferredScenes` instead.

## Known architectural limitation: no "actually spoken" signal

The engine gives no reliable way to tell whether a TopicInfo **was actually spoken** or was **only built as a candidate** for the dialogue menu. When the player presses E on an NPC, DialogueItem::Ctor, PopulateTopicInfo, SetSubtitle and ConstructResponse all fire for every menu candidate in a burst of about 3 ms. Because of this, both history logging and subtitle blanking depend on stacked heuristics:
- Ctor↔Populate correlation (50 ms)
- A duplicate window (5 s)
- A (speaker, TopicInfo) cooldown (5 s)
- A text cooldown (5 s)
- A candidate-burst filter (100 ms plus `MenuTopicManager::dialogueList` membership)
- A `[STALE CACHE]` diagnostic for when a cached decision leaks to a different TopicInfo

Known deferred bug: a greeting subtitle can reappear when the NPC gives no greeting. The roughly 800-line `Hook_PopulateTopicInfo` is deliberately left as it is until the planned rewrite, which should start by finding a definitive "spoken" signal. Until then, don't pile more heuristics onto it without a log that shows the symptom.
